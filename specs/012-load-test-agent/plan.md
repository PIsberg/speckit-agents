# Implementation Plan: Opt-in load-test role

**Branch**: `012-load-test-agent` | **Date**: 2026-11-22 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/012-load-test-agent/spec.md`

## Summary

A ninth agent, `load-tester`, joins a `/speckit-team` run only on `--load-test` or when named in
`--team`, after the last green round and before spec-gatekeeper. It writes load tests (a reduced size
that runs in the project's ordinary test command, the full sweep behind an environment variable) and
one record file, `specs/<feature>/load-test.md`, runs them, and ends `PASS`, `FAIL` or `NOT MEASURED`.
A FAIL stops the run for the user. The hook gets one new lane rule, `load` (D1), one CLI mode,
`probe`, for the noisy-run warning (D2), and the role in `TEAM_ROLES`; the installer generates its
role skill for `--team skill-agents` from the agent file as it does for the other seven. Every
measurement rule of the article is prompt text in `agents/load-tester.md`, pinned by
`test/install.test.mjs`, and measured by six scored cases in `tools/eval.mjs` (SC-001, SC-002, SC-004,
SC-006). The interface is in [contracts/load-tester.md](contracts/load-tester.md); the by-hand checks
in [quickstart.md](quickstart.md).

## Technical Context

**Language/Version**: JavaScript (ES modules), Node 22 or newer (constitution IV)

**Primary Dependencies**: none beyond the Node standard library; `probe` uses `node:os` and `node:crypto`

**Storage**: no new hook state. The role's records are one Markdown file per feature,
`specs/<feature>/load-test.md` (contracts/load-tester.md section 5)

**Testing**: `npm test` (`tools/test.mjs`, `node --test`); `test/e2e.test.mjs` for the agent's hook
wiring in a real Claude Code session against the fake API; `tools/eval.mjs` scored cases by hand

**Target Platform**: Windows (Git Bash, PowerShell), macOS, Linux (constitution VII)

**Project Type**: Claude Code agent team: agents, skills, one hook script, an installer

**Performance Goals**: a run without the role starts no added process (FR-002); `probe` takes about
1.5 s per call (a 1,000 ms load sample and a fixed hashing workload), two calls per load-tester run

**Constraints**: the generated role skill stays under 150 lines (`test/skills.test.mjs`), so the agent
body is at most 100 lines; `skills/speckit-team/SKILL.md` stays under 500 (396 now, about 20 added)

**Scale/Scope**: 4 source files changed (`hooks/speckit-team.mjs`, `install.mjs`,
`skills/speckit-team/SKILL.md`, `mods/speckit-board/hooks/model.ts`), 1 agent added, 2 tools changed
(`tools/full-run.mjs`, `tools/eval.mjs`), 1 fixture tree added, docs

### Design

- **Membership** (FR-001, FR-002, FR-017): `load-tester` goes into `TEAM_ROLES` (hook) and `AGENTS`
  (`install.mjs`) between `implementer` and `spec-gatekeeper`, the pipeline order the `Team:` line uses.
  `CORE_ROLES` is unchanged, so a launch with no `Team:` line never records it. `typedRoles` skips a
  leading `--load-test` as it skips `--security`. `SETTINGS_GATES`' SubagentStart matcher is
  `AGENTS.join('|')`, so the project block reaches the role with no new entry, and the matcher fires
  only when load-tester starts: a run without it starts no added process.
- **Lane `load`** (FR-004, D1): a path is in the lane when it is a test path (`isTest`, so
  `.specify/test-paths` applies, `!` lines included) with a `load` part, or the record file. Production
  code, functional tests, `tasks.md`, spec and plan, and `.specify/` are outside it. `scope load` runs in
  the gate's process (`gate scope load`, as test-writer's `gate scope tests`), so the audit gate holds
  for the role (FR-017) and the start record for `lane load` at Stop is written by the gate.
  `ROLE_LANES` gets `"load-tester": ['load']` for the role skill (FR-003).
- **Verdict** (FR-006): `ends PASS FAIL "NOT MEASURED"` at SubagentHandback and Stop, as
  security-reviewer's `ends`. Nothing records it: the skill routes on it.
- **Skill-agents** (FR-003, D3): `speckit-role-load-tester` is generated by `install.mjs: roleSkill`;
  the hook's audit gate on a role skill call (`gate`, the list `['test-writer', 'implementer',
  'spec-gatekeeper']`) gains `load-tester`, matching the agent's `gate`. The report's last line is not
  hook-checked in that mode, as for every role there.
- **Pipeline step** (FR-005, FR-010, FR-016, D6): a new `## 5b. Load test: load-tester` in the skill,
  between `## 4-5.` and `## 6.`. FAIL, or any other last line, is a **Stop:** with three options: fix
  (implementer with `last round`, then load-tester again), accept, or stop. NOT MEASURED goes on and is
  listed at hand-over with its reason. load-tester's files are committed in the message that launches
  spec-gatekeeper (at hand-over when it is not in the team); the last round was committed with
  load-tester's launch, so every uncommitted change then is load-tester's. On accept, that Bash call
  commits only the record `specs/<feature>/load-test.md` and stashes the rest with `git stash push
  --include-untracked -m "load-tester: accepted FAIL"`, so no breaching load test reaches
  spec-gatekeeper's gate 3 (`agents/spec-gatekeeper.md`, Process 3) or CI; hand-over lists the FAIL and
  the stash with its files. An opt-in role not asked for gets no skipped row, so a run without it hands
  over as before (FR-002).
- **Noisy-run probe** (FR-013, D2): `node "<hook>" probe` prints the machine's busy share over a
  1,000 ms sample and the time of a fixed workload; `probe --since <busy>,<ms>` adds a `noisy:` line per
  threshold crossed. The agent runs it before and after its measurements and copies the `noisy:` lines
  into its report and record. A CLI like `check`, never a hook entry.
- **Measurement rules** (FR-007 to FR-016): sections of `agents/load-tester.md`: Inputs, Lane, Process
  (load surface; instruments; budgets; workloads; harness and record), Verdict, Report. The defaults
  (10%, 20%, 4 doublings, a 2.2x margin) are the spec's Assumptions; a project's instructions or
  constitution may tighten them.
- **Scored cases** (SC-001, SC-002, SC-004, SC-006): `load-quadratic` (right: FAIL), `load-linear`
  (PASS), `load-pinned`, `load-empty`, `load-skipped` (right: not PASS), `load-noisy` (the linear
  fixture with 30% of the cores busy; right: PASS and a noisy warning). One turn each on a finished,
  audited feature, like the gate cases; `--skill-agents` gives SC-004's second arm. Running them is
  D5. load-tester's word is read by the existing `tools/eval.mjs: gateWord`, which gains a `words`
  option and a `lastLineOnly` mode (FR-006: the report's last line is the verdict); no second parser.

## Decisions

### D1: How does the hook tell a load test from a functional test (FR-004)?

Answer (2026-11-22): A, as recommended

- **A (recommended): a built-in pattern.** In lane: a test path (`isTest`) with a `load` part, matched
  by `/(^|[\/._-])load([\/._-]|$)/i` or `/[a-z0-9]Load(Tests?|IT|Spec)\.[A-Za-z]+$/`, plus
  `^specs/[^/]+/load-test\.md$`. `test/load/x.test.mjs`, `x.load.test.js`, `tests/test_load_x.py`,
  `x_load_test.go` and `SumLoadTest.java` are in; `test/loader.test.js`, `download.test.js` and every
  functional test are out. Go benchmarks go in a `_load_test.go` file, not beside the functional ones.
  A `.specify/test-paths` `!` line that takes a path out of the tests takes it out of the lane too. No
  new config file. As written: T001, T002, contracts/load-tester.md section 3.
- **B: any test file.** The lane is test-writer's minus `tasks.md`; FR-004's "MUST NOT change functional
  tests" is held by the agent's text only, and a load-tester that edits `test/math.test.js` passes its
  lane check. T001 loses its functional-test denial; T002 is about 5 lines shorter.
- **C: a project file `.specify/load-paths`**, regex lines like `.specify/test-paths`, A's pattern when
  absent. One more file to parse, a bad line makes the lane undecidable (the same refusal as a bad
  test-paths line), and README's "Test files" section grows. T001 and T002 grow by about a third; T025
  documents the file.
  Spec: under Assumptions: add "- A project may name its load-test paths in `.specify/load-paths`, one regular expression per line."

### D2: Where does the noisy-run measurement come from (FR-013, SC-006)?

Answer (2026-11-22): A, as recommended

- **A (recommended): a `probe` CLI mode of the hook.** The thresholds are exact numbers (10%, 20%) and
  SC-006 asks for the warning every time, so a script computes them rather than a model retyping a
  probe per run (constitution review criterion "prefer a script"). About 40 lines in the hook and one
  test slice (T014, T015); the agent body names two commands. Runs wherever the hook runs, whatever the
  project's stack.
- **B: the agent measures it with the project's own tools**, as its body describes. No hook code; T014
  and T015 go, round 2 has three slices. The reading differs by stack and OS (`os.loadavg()` is all
  zeros on Windows), and whether the warning appears depends on the model: SC-006 is then measured only
  by the `load-noisy` case.

### D3: What does "the same guardrails" mean for the role skill (FR-003, US1-4)?

Answer (2026-11-22): A, as recommended

- **A (recommended): the guardrails `--team skill-agents` gives every role.** The lane (`scope role`,
  `lane role` through `ROLE_LANES`) and the audit gate on the role's call hold; the report's last line
  is not checked by the hook in that mode, as for every role there (the hook's skill-agents start
  message says so). The skill still routes a missing line as a FAIL (step 5b). As written: T004, T007.
  Spec: FR-003: "`--team skill-agents`, with the same lane, the same verdict lines and the same guardrails." becomes "`--team skill-agents`, with the same lane and the same verdict lines; the guardrails are those each mode gives every role (in skill-agents mode the hook does not check a report's last line)."
  Spec: US1-4: "the verdict is the same and the same guardrails hold." becomes "the verdict is the same and each mode's guardrails hold for the role as for every other role."
- **B: also check load-tester's last line in skill-agents mode**, read as `recordReport` reads the
  auditor's (the next Skill call's first `args` line, or the Stop's last message), and send it back
  once when it is none of the three. New hook code in `closeRole`, one more slice (round 2 is full, so
  round 3, about 6 test cases in `test/hook.test.mjs`), and the start message's "Not enforced" list changes. No spec
  change.

### D4: May the team be load-tester alone (edge case "a team that has no implementer")?

Answer (2026-11-22): A, as recommended

- **A (recommended): no.** The existing refusal stands: a team needs test-writer or implementer, so a
  builder-less run is `--team test-writer,load-tester`, and load-tester measures the code as it stands
  after test-writer's RED. No change to `## Team`'s refusals or to the hook.
- **B: yes, `--team load-tester` measures the active feature's code.** The refusal becomes "none of
  test-writer, implementer or load-tester"; with no active feature there is no folder for the record, so
  the role reports NOT MEASURED. T008 and T009 grow by the refusal and the start condition (step 5b
  starts at once).
  Spec: under Edge Cases: add "- A team of load-tester alone measures the active feature's code as it stands; with no active feature it reports NOT MEASURED."

### D5: Are the scored load cases run before merge, and by whom (SC-001, SC-002, SC-004, SC-006)?

Answer (2026-11-22): A, as recommended

- **A (recommended): not a task.** T022 and T023 build the six cases and test their scoring offline; the
  owner runs quickstart.md Q2 by hand (5 runs of each case, 5 more of `load-quadratic` with
  `--skill-agents`: 35 runs on real models; `tools/full-run.mjs` puts a whole run at $2 to $4, a one-turn
  case less, not measured) and the PR body records the counts. Until then README says the cases exist and
  have not run.
- **B: a last-round task runs them** with `tools/eval.mjs --login`, records the counts in
  `docs/live-results.md` and `docs/measurements.md`, and the PR waits for it. One more task after T025,
  the same 35 runs and their cost on the implementer's login.

### D6: What happens to a breaching load test when the user accepts a FAIL (FR-010, FR-016, US5-1)?

Answer (2026-11-22): A, as recommended

Committed as written, a breaching load test fails the project's test command, so spec-gatekeeper's gate
3 ends REJECTED and CI is red after merge.

- **A (recommended): commit the record, stash the load tests.** As in "Pipeline step": the accept
  path's Bash call commits `specs/<feature>/load-test.md` and stashes every other change of
  load-tester's; hand-over names the stash and its files (`git stash pop` restores them after a fix).
  Gate 3 and CI run without the breach. The record keeps the failing readings, so the acceptance is
  not silent (FR-010). The main session cannot tell from the report which file holds which measurement,
  so the passing load tests of that run are stashed too. An accepted instrument FAIL (empty result set,
  stale build) and an accepted refused report take the same path. With no spec-gatekeeper in the team
  (D4), the stash comes before the hand-over commit. No new code: two git commands in skill text. As
  written: T008, T009, contracts/load-tester.md section 5.
  Spec: FR-016: "command and a written procedure for the full sweep (US5)." becomes "command and a written procedure for the full sweep (US5); after a FAIL the user accepts, the run commits only the record and stashes the load tests, naming the stash at hand-over."
- **B: re-baseline on accept.** load-tester is launched again with `accepted`: it sets each failing
  gating ceiling to the new reading times its margin, adds a `## Budgets` row with the failing readings,
  the date and "accepted by the user", reruns the reduced tests green and ends PASS; its files are
  committed as after any PASS, so every load test stays in the test command. One more load-tester
  launch per accepted FAIL (cost not measured). An instrument FAIL has no ceiling to move, so it still
  takes A's stash. The agent body gains about 4 lines toward its 100-line cap; T016 and T017 add the
  `accepted` rule, T008 and T009 the relaunch beside A's stash.
  Spec: FR-012: "- **FR-012**: Every new ceiling MUST come from a recorded failing first run and a stated margin (US3)." becomes "- **FR-012**: Every new ceiling MUST come from a recorded failing first run and a stated margin, or from a breach the user accepted, recorded with its readings and date (US3)."
